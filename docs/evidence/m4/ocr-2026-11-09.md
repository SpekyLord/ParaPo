# Overnight OCR investigation — 2026-11-09

We tested saved sign crops on the connected TECNO KJ8, Android 14/API 34, using the app's bundled ML Kit Latin 16.0.1. No roadside collection, detector retraining, new dependency, upload, or route-data change was involved. The shared `SignTextReader` remains the recognition entry point.

## Fixed experiment and results

The first comparison used the ten crops from the Nov. 8 diagnostic. Each crop was tested unchanged and with three predetermined transformations: a neutral-gray border of `max(16, round(height × 0.2))` pixels, grayscale autocontrast with a 1% cutoff, or 2× horizontal bicubic stretching. We ran all 40 prepared inputs twice, reversing the order on the second pass. Words and API errors were identical between passes. Timing varied; repeated observations are not independent samples.

These are exploratory hypotheses about crop boundaries, contrast, and character geometry. They are not endorsed ML Kit settings. Google's [official input guidance](https://developers.google.com/ml-kit/vision/text-recognition/v2/android) emphasizes sufficient character detail and focus; these transformations cannot recover missing image information.

The denominator of nine known numeric codes includes unsupported Route 11. Unknown text/route truth on image 34 is excluded from accuracy denominators and remains counted separately. Wider text looked better by CER but did not improve code identification; it produced strings such as `037` and `03N`, which remain unsupported/unreadable. These observed failure strings were added to the shared Android/Python matcher cases without relaxing matching.

The gray border recovered image 27 as `UNGKA-LOLO CITYPROPER VIL CRU 03` and image 28 as `11/ TCUDLAPAZ- CITY PROPER`. The latter remains outside supported coverage. Contrast lost the previously correct Route 3 read on image 24. Image 18 still returned empty with the border; a clean full transcription was not recovered from it.

We then checked only the original-versus-border pair on the other **28 photos / 30 signs**, again in forward and reverse order: 60 inputs per pass. These photos were already reviewed development evidence, including previously inspected test photos. They are not a new held-out set. No further transformation tuning followed.

The border did not generalize as a blanket improvement. For example, image 13 changed from `JARO LIKO` to `JARO LIKọ`, losing an exact alias. Its independent route label is unknown, so this is a text/alias regression, not a claimed ground-truth route error. Known-route correctness did not improve. Unknown-route predictions are listed separately in the reports; they are never counted as verified correct.

## Narrow fix that reached the app

Both raw passes hit the same real API error on image 15: its valid sign crop is **43×23 pixels**. ML Kit returned `InputImage width and height should be at least 32!`. In the live pipeline, an OCR task failure follows the recognition-failure path; this case can instead be handled before calling the API.

`SignTextReader` now adds only enough centered gray canvas to make each side at least 32 pixels. It preserves source pixels and bitmap density, performs no rescaling, leaves already-large inputs unchanged, and recycles its temporary bitmap when recognition completes or throws. The diagnostic records original and actual recognition dimensions plus input policy `minimum-32-gray-padding-v1`.

On the phone, image 15 now enters recognition at **43×32**, produces an explicit empty result, and has **no API error**. This fixes input handling, not readability. The post-fix confirmation run processed all 60 inputs with zero API errors. A separate instrumented test verifies preserved pixels, padding placement, unchanged large images, retained caller ownership, and a completed ML Kit task for an undersized input.

No general border, contrast adjustment, horizontal stretching, fuzzy alias, or numeric substitution was enabled in ordinary scanning. Some legible condensed/angled text still yields no blocks or unusable words. Those observations locate the failure in reading rather than proving a particular internal ML Kit cause. Fused text such as `03UNGKA` is still not a safe independent numeric token.
